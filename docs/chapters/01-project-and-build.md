# 1. Project, Architecture, and Build Configuration

## What This Project Actually Does

Arrakis: Harvester Down is an interactive, real-time three-dimensional rescue game. The player pilots an ornithopter above a mathematical desert. A moving spice harvester periodically releases workers while a sandworm pursues it. The player must fly to each group, slow down, descend, hold the rescue control, carry a limited number of workers, and deliver them to a landing pad. A worker merely collected aboard is not yet a scored survivor. The game contains a title screen, timed mission, pause overlay, debrief, retry, escalating later missions, and a best score retained in memory.

The program is not a 3D-model viewer and does not parse OBJ files. Its cubes, cylinders, spheres, aerofoil blades, desert grid, rings, eroded rocks, people, worm body, mouth, and teeth are generated in code. Colored materials and procedural shaders replace image textures for world objects. Sound files are the actual disk-loaded runtime assets. The original screenshots, worm photograph, and proposal in `docs/reference/` are human references, not inputs used to draw a frame.

The implementation is C++17 with an OpenGL 3.3 core graphics context. GLFW creates the window, receives events, reports time, and provides driver procedure addresses. GLAD turns those addresses into callable OpenGL functions. GLM supplies vectors, matrices, angle conversion, interpolation, and camera transforms. Miniaudio decodes and spatializes sounds, mixes them, and feeds an operating-system audio device. Python and ReportLab are documentation-generation dependencies; neither is required to play the game.

## How to Read the Detailed Explanations

Chapter 4 explains every mission field, state, helper, update path, and deterministic test in `src/arrakis_game.h` and `tests/arrakis_tests.h`. Chapter 5 explains the HUD, bitmap font, radar, and sandworm mesh/animation code. Chapter 6 explains the audio integration in detail and the retained vendor libraries by functional family. Chapter 7 explains the PDF generation tool itself. The numbered appendices include complete retained code and configuration, including miniaudio's large vendor implementation.

Code-range headings refer to physical source-file line numbers. Their purpose is to make small implementation details locatable, not to turn comments or braces into imaginary features. A range can contain several repeated draw calls or assertions; the explanation accounts for what their individual parameters or conditions do. Blank lines provide visual separation and execute nothing. A comment documents an intention but does not run; when a comment and executable behavior disagree, this explanation prioritizes the behavior. The complete source snapshot, file hashes, and source line counts are supplied in the appendix and `docs/documentation_manifest.json`.

Application code is explained much more finely than the third-party libraries: the latter are grouped by algorithms and API families, with their existing comments and full source retained. A library line listing is a reference, not a claim that every branch in every operating-system backend has been rewritten as a unique prose explanation. This distinction matters because miniaudio alone contains approximately 96,000 lines and many backends that this Windows game never executes. External installed GLFW, GLM, and GLAD headers are not project-authored files and are not bundled by this cleanup.

## Repository Organization and Cleanup Decisions

`src/` holds five application source/header files. `src/arrakis.cpp` remains the executable's main translation unit: it introduces shared globals and drawing types, then includes project headers where their dependent names are available. The headers are not independently compiled C++ libraries. In particular, the game header assumes terrain and flight state have already been declared, and the worm header assumes rendering helpers exist. This arrangement is preserved instead of introducing a risky architecture rewrite during folder cleanup.

`tests/arrakis_tests.h` contains deterministic logic tests. The main program includes it through a dedicated compiler include directory. Running `--test-game` returns before GLFW window or audio initialization, so tests do not need a desktop. The test code still links into the same executable. The cleanup does not claim to have extracted a separate test library.

`third_party/glad/` retains the generated loader implementation; `third_party/miniaudio/` retains the audio header and its two-line implementation translation unit. These files are runtime dependencies, not unnecessary downloads. Their license statements and embedded documentation remain intact. `assets/audio/` holds the eight primary sounds requested by the application plus the retained Kenney license notice. Retaining that notice does not establish the provenance or licensing of every unrelated MP3 file; the repository contains no complete per-file sound attribution manifest.

`docs/chapters/` contains this editable explanation. `docs/reference/` preserves the original proposal PDF, `arrakis.png`, and `sandworm.jpg`. `tools/` contains the PDF generator and Python dependency constraints. CMake, the vcpkg manifest, README, alternative Visual Studio project, and shared editor settings stay at the root because they are entry points to building or understanding the repository.

The removed folders were `dune spice harvester/`, `low_poly_rocks/`, `ornithopter/`, `spice tank/`, and `thumper/`. They contained unused imported geometry, materials, and textures. Nothing in the renderer loads them; retaining them would imply a nonexistent model-loading pipeline. The old `build/`, `x64/`, and `vcpkg_installed/` folders were generated caches/output rather than source. A new ignored `build/rescue/` is produced when verifying the organized project. It is intentional that verification leaves a runnable build rather than pretending builds never create files.

The unused `stb_vorbis.c`, redundant Ogg delivery sound, and downloaded Kenney fallback pack were removed. The miniaudio implementation never enabled its optional stb Vorbis adapter; the retained selected sounds are WAV or MP3. The audio candidate lists still allow alternate filenames, including Ogg names, but such fallbacks are not included and the default build has no enabled Vorbis decoder. The previous `CODE_EXPLANATION.txt` and historical README sections described an earlier renderer and contradictory controls; the current detailed chapters replace those notes rather than preserving two conflicting manuals. The machine-specific Visual Studio `.user` file and unrelated C/C++ Runner editor settings were removed; the debugger launch was corrected to the actual MSVC executable.

## C++ Foundations Used Throughout the Code

An `int` stores integer counts or selections. A `float` stores a single-precision real value such as elapsed seconds, speed, height, or color. A `bool` stores true or false. A structure groups related fields, for example a particle's position, velocity, lifetime, size, and opacity. `enum class` gives names to state choices and prevents accidentally confusing one enumeration with another. `std::vector` is a resizable contiguous container; the code uses it for vertices, indices, workers, groups, and particles. `std::array` is fixed-size. A `std::string` owns text, such as a sound filename or HUD message.

The `g_` naming convention marks global application state. Globals are shared across functions and included headers; they are not automatically thread-safe. Most game/rendering code executes on the main thread. Miniaudio also runs its own processing threads internally. A reference parameter such as `const Mesh&` avoids copying while disallowing changes through that parameter. A non-const reference allows a helper to modify the caller's object. A pointer represents an address and can be null. OpenGL object IDs are integer handles into driver-managed resources, not pointers to their data.

`static` variables inside functions retain their values across calls. That is why a seeded random generator produces a deterministic sequence rather than restarting every frame, and why cached uniform locations avoid repeated lookups. At namespace scope, `static` gives internal linkage. `inline` permits definitions in a header to satisfy C++'s multiple-definition rules; it is not a guarantee that the compiler literally substitutes the function's body at every call. `#pragma once` or a matching `#ifndef`/`#define` header guard prevents the same header from being included twice into one translation unit.

Floating-point literals ending in `f`, such as `0.35f`, specify float precision. Vector arithmetic applies component-wise or according to GLM's defined operators. `std::sin` and `std::cos` expect radians; aircraft headings are stored in degrees and converted before trigonometry or rotations. A `glm::vec2` often represents horizontal coordinates, a `glm::vec3` a world point/direction or RGB color, a `glm::vec4` homogeneous coordinates or RGBA. Normalizing changes a nonzero vector to unit length without changing direction. Clamping restricts a value to a permitted interval. Linear interpolation `mix(a,b,t)` computes `a*(1-t)+b*t`; exponential interpolation factors such as `1-exp(-rate*dt)` implement a time-based approach to a target.

Triangles are the basic filled rendering primitive. A vertex contains position and other per-vertex attributes. An index selects a vertex; indexed triangles reuse data. A shader is a GPU program; GLSL vertex shaders transform points, and fragment shaders decide the color for a covered pixel/sample. A model matrix converts local object coordinates to world space, a view matrix converts the world into camera space, and a projection matrix produces clip-space coordinates. Matrix multiplication order matters. An inverse-transpose normal matrix preserves normal direction under nonuniform scaling. A framebuffer directs rendering to either the screen or off-screen attachments such as the shadow depth texture.

## CMakeLists.txt: Lines 1-18, Project and Compilation Units

Line 1 requires CMake 3.20 or newer; an older installation stops configuration rather than attempting unsupported syntax. Line 3 names the project `Arrakis` and, without a `LANGUAGES` restriction, enables the normal C and C++ compiler discovery needed by the C loader and C++ application. Lines 5-6 request C++17 and require it instead of silently falling back to an older language mode.

Lines 8-18 create an executable target called `Arrakis`. `src/arrakis.cpp` is compiled as C++; `third_party/glad/glad.c` is compiled as C; `third_party/miniaudio/miniaudio_impl.cpp` is compiled as C++ and instantiates miniaudio's implementation exactly once. The four application headers and the test header are listed as target sources primarily for build dependency tracking and IDE visibility. A header is not an additional independently linked object just because it appears in this list.

## CMakeLists.txt: Lines 20-30, Dependency Discovery and Include Paths

Line 20 requires OpenGL and provides the imported `OpenGL::GL` target. On this Windows installation it links the system OpenGL library. Lines 22-24 search for `glad/glad.h`, `GLFW/glfw3.h`, and `glm/glm.hpp`. The specified E-drive directories are hints; `REQUIRED` makes configuration fail when a dependency cannot be found. GLM additionally searches the optional manifest-installed `vcpkg_installed/x64-windows/include` directory. Removing the installed cache does not remove `vcpkg.json`, so it can be regenerated. The successfully verified setup has GLM available at `E:/glm` independently of that cache.

Line 25 searches for a GLFW binary library named `glfw3` or `glfw`. Headers tell the compiler what functions exist, but a library supplies their linked machine code; both are necessary. Lines 26-30 apply discovered include directories only to this executable, using `PRIVATE` rather than publishing them to consumers. The explicit `tests` include directory resolves `arrakis_tests.h` after its move. The miniaudio include directory resolves `miniaudio.h` from the application audio header; the implementation file also finds it in its own directory. Project headers alongside `src/arrakis.cpp` continue to resolve through normal quoted-include search rules.

Cache overrides such as `-DGLFW_LIBRARY=C:/deps/lib/glfw3.lib` let another machine supply its installation. An include-directory override must point at the parent of `GLFW/`, `glad/`, or `glm/`, not at the individual header file. The retained GLAD C loader was generated for core GL 4.6 even though the application requests a 3.3 context. Its matching declarations are required for compilation; the context's supported version determines which function groups actually load. A randomly different GLAD generation can therefore fail to compile this loader even when the application only uses 3.3 features.

## CMakeLists.txt: Lines 32-43, Definitions and Linking

`target_compile_definitions` passes `GLFW_INCLUDE_NONE` to compilation. It asks GLFW not to include a competing system OpenGL header, because GLAD must provide the function declarations and pointers. `PRIVATE` restricts the definition to this executable. `target_link_libraries` links GLFW and `OpenGL::GL`. Miniaudio's platform backend implementation comes from the vendored implementation unit; it is not a separately downloaded miniaudio library. GLM is header-only and does not need a GLM binary here.

The verified Release build emits linker warning LNK4098 about `MSVCRTD` conflicting with other runtime libraries. This is a property of the existing local library/runtime combination, not a missing source file introduced by the reorganization. The executable and tests succeed, but rebuilding GLFW with the matching release runtime is preferable to hiding the diagnostic. The project does not add `/NODEFAULTLIB` to conceal it.

## CMakeLists.txt: Lines 45-56, Runtime Files and Tests

Lines 46-50 add a post-build command to the actual executable target. CMake invokes its own executable using the cross-platform `-E copy_directory` helper, copying the complete `assets/audio` directory under the chosen executable directory. `$<TARGET_FILE_DIR:Arrakis>` is a generator expression evaluated for the selected configuration, so a Visual Studio Release build receives files beneath `Release/assets/audio/`, and Debug receives its own copy. It avoids a hardcoded configuration or user path.

Line 51 sets the generated Visual Studio debugger's working directory to the executable directory. The audio lookup first checks `assets/audio/` relative to its current working directory, then four ancestor directories. This supports root launches, normal build-directory launches, and packaged launches from the executable directory. The implementation still uses relative working-directory lookup, not an absolute path derived from the executable; arbitrary unrelated working directories are not guaranteed to resolve sounds. Failure to resolve a sound does not terminate gameplay.

Line 53 loads CTest integration and the standard `BUILD_TESTING` option. Lines 54-56 register `RescueMissionLogic` only when testing is enabled. The command references the executable target and passes `--test-game`; CMake resolves the right built executable for the selected configuration. `ctest --test-dir build/rescue -C Release --output-on-failure` executes it and reports details on failure. No graphical context is requested for this command.

## The Alternative Visual Studio Project

`Arrakis_001.vcxproj` is MSBuild XML. The XML declaration identifies encoding. `<Project DefaultTargets="Build">` selects the default target and the Visual C++ MSBuild namespace. The `ProjectConfigurations` item group defines four pairs: Debug/Win32, Release/Win32, Debug/x64, and Release/x64. Each pair records both configuration and platform. The globals record Visual C++ project version 17, project identity GUID, `Win32Proj` keyword, root namespace, and the Windows 10 SDK family. The GUID identifies this project in the IDE; it does not change gameplay.

The first imported Microsoft defaults file supplies standard properties. Four conditional configuration groups choose an Application executable, debug-library selection, toolset v143, Unicode character set, and Release whole-program optimization. Unicode here selects the Windows character-set build property; it does not automatically make every game string Unicode. `Microsoft.Cpp.props` brings in further toolchain settings. Empty extension/shared import groups are standard places for optional tool integration. The four property-sheet import groups allow per-user platform properties if their files exist. The empty user-macros group is a conventional customization point.

The x64 property groups retain E-drive include/library paths. Release/x64 also allows optional vcpkg-installed GLM headers; Debug/x64 uses the laboratory GLM path. These are local-installation conveniences, not portable dependency provisioning. Although Win32 configurations are listed, corresponding 32-bit dependency paths are not configured here; the verified build is x64 through CMake, not a claim that all four standalone configurations are independently tested.

The common item-definition group sets C++17, `GLFW_INCLUDE_NONE`, and the relocated tests/miniaudio include directories. Its post-build event uses `xcopy /E /I /Y`: `/E` includes subdirectories, `/I` treats the destination as a directory, and `/Y` overwrites without prompting. The command quotes directories to survive spaces in the project path and places audio below `$(OutDir)`. This event is Windows-specific; the primary CMake copy helper is cross-platform.

Each configuration's compiler group sets warning level 3, SDL checks, relevant console/debug/release macros, and conformance mode. Release additionally enables function-level linking and intrinsic functions. Link settings select a console executable and generate debug information. The x64 linker groups add `glfw3.lib` and `opengl32.lib`, preserving inherited dependencies with `%(AdditionalDependencies)`. `$(...)` is an MSBuild property substitution; `%(...)` refers to inherited item metadata. The source item group compiles the three relocated C/C++ units. The `None` item displays the vcpkg manifest without compiling it. Header items display the five relocated application/test headers. The final Microsoft C++ targets import provides actual compile/link targets; the empty extension-target group is a standard trailing integration hook.

`Arrakis_001.vcxproj.filters` is only IDE presentation. Its Source Files, Header Files, and Resource Files filters have stable identifiers and extension lists. Compile entries place the three actual source units under Source Files. Header entries place audio, game, worm, HUD, and tests under Header Files. The manifest is a `None` item. Filters do not move files, compile resources, or alter output; changing only the filter file never repairs a broken source path in the project itself.

## Shared Editor and Dependency Configuration

`.vscode/c_cpp_properties.json` contains one IntelliSense configuration named `Win32-MSVC`. Its recursive workspace include path sees relocated headers; its additional E-drive paths expose installed GLFW/GLAD and GLM. `compilerPath` selects `cl.exe`, C language mode is C17, C++ language mode is C++17, and IntelliSense uses the Windows MSVC x64 model. The final version value 4 identifies the extension's settings schema, not the compiler version. These settings assist editing and do not replace CMake's real compilation flags.

`.vscode/launch.json` uses the debugger schema version 0.2.0. Its single configuration is named Arrakis (CMake Release), has `type: cppvsdbg` for the Visual Studio Windows debugger, and `request: launch` to start rather than attach. The empty argument array launches normal gameplay. `stopAtEntry: false` avoids an automatic initial breakpoint. The integrated terminal displays console messages, the working directory is `${workspaceFolder}`, and the program path selects `build/rescue/Release/Arrakis.exe`. This configuration assumes that Release has already been built; it does not silently build or select a Debug executable.

`vcpkg.json` is a JSON manifest. Its `dependencies` array contains only `glm`; it does not install GLFW, GLAD, or miniaudio. Its `builtin-baseline` records a specific vcpkg registry revision for reproducible version selection. A manifest's existence alone does not run installation without a configured vcpkg workflow/toolchain. The existing build prints a notice that manifest mode is disabled; this is not a build failure because independently discovered GLM satisfies the dependency.

## Every .gitignore Rule and Why It Exists

Git ignores are repository hygiene, not deletion instructions and not security boundaries. A pattern never removes a tracked file or prevents the program from using an ignored file already on disk. A leading `/` anchors the pattern to the repository root. A trailing `/` targets directories. `*` matches arbitrary text. A comment beginning with `#` has no matching effect.

`/build/`, `/build-*/`, `/out/`, `/x64/`, and `/x86/` cover root build/output folders. `Debug/`, `Release/`, `RelWithDebInfo/`, and `MinSizeRel/` exclude generated configuration directories at any depth. `CMakeFiles/`, `CMakeCache.txt`, `cmake_install.cmake`, `install_manifest.txt`, `CTestTestfile.cmake`, `Testing/`, and `_deps/` cover CMake discovery state, generated scripts, test output, and fetched dependencies. `CMakeUserPresets.json` is a personal configuration file; a shared `CMakePresets.json`, if later added, remains trackable. `/vcpkg_installed/` excludes reproducible installed-package copies, while `vcpkg.json` remains included.

`*.o` and `*.a` are common Unix object/static-library outputs. `*.exe`, `*.dll`, `*.so`, `*.so.*`, `*.dylib`, and `*.lib` cover executables/shared/static libraries on Windows, Linux, and macOS. `*.pdb` and `*.idb` are debug databases; `*.ilk` is incremental-link state; `*.exp` is exported-symbol linker output; `*.pch` is a precompiled header; `*.tlog` is MSBuild tracking; `*.obj.enc` is Edit-and-Continue object state; `*.exe.recipe` is a generated executable recipe; `*.log` is log output. The broad old `*.obj` rule is deliberately absent because Wavefront 3D model files use the same extension as Windows object files. MSVC object files belong in the already ignored build directories rather than forcing all future model assets invisible to Git.

`.vs/`, `*.vcxproj.user`, `*.suo`, `*.user`, `*.VC.db`, `*.VC.VC.opendb`, and `.vscode/ipch/` exclude user-specific IDE caches and preferences. Shared `.vcxproj`, `.vcxproj.filters`, `.sln`, launch, and IntelliSense files are not globally hidden. `__pycache__/`, `*.py[cod]`, and `.venv/` exclude Python bytecode or a local virtual environment. `/docs/.cache/` provides an ignored place for generated documentation intermediates; the requested PDF is intentionally not ignored. `Thumbs.db`, `ehthumbs.db`, `Desktop.ini`, and `.DS_Store` cover operating-system folder metadata. `*~`, `*.swp`, and `*.swo` cover common editor backups/swap files. No blanket PDF, PNG, JPG, WAV, or MP3 pattern hides required documentation or assets.

## Verified Cleanup Behavior and Remaining Limits

The organized project was configured from a clean build directory and built in MSVC Release/x64. The alternative standalone Visual Studio project was also built successfully in Release/x64, with its output and intermediates explicitly directed beneath `build/native/` and vcpkg integration disabled for that check. Its post-build event copied all eight sounds and the retained license. `RescueMissionLogic` passed. The normal render, breach, mouse-steering/camera, and pursuit smoke tests each rendered 120 frames and reported success on an Intel Iris Xe OpenGL 3.3 driver. An additional smoke run from the executable directory also loaded every selected sound. These checks exercise actual relocated runtime assets rather than only searching source text for filenames. The standalone build additionally reports a vendor warning C4244 at miniaudio line 80532 about narrowing an unsigned 64-bit value to 32 bits; the vendored code is retained unchanged rather than modifying library internals during cleanup.

The post-build asset copy is not an installer. It is triggered by a build of the executable target, and does not continuously watch asset edits. Rebuild the target or recopy assets if only sound files change after a previous build. Tests validate deterministic mechanics and finite scripted rendering windows, not every possible human flight path. No network, save file, persistent leaderboard, imported-model loader, cloud sky renderer, or image-based worm texture is implemented. Those distinctions are documented so the explanation remains a description of existing functionality rather than an aspirational feature list.
